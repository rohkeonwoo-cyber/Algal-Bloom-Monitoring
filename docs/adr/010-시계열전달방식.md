# ADR-010 · 시계열은 구간값과 래스터를 서로 다른 속도로 전달한다

- 상태: 채택
- 날짜: 2026-09-16

## 맥락

시계열 슬라이더를 끌 때 프레임마다 래스터 타일을 새로 요청하면 네트워크 왕복이 매번 들어가
반드시 버벅인다. 반면 두 자료의 크기는 3자릿수 차이가 난다.

| 자료 | 크기 |
|---|---|
| 구간값 (1,340구간 × 133프레임 × 2바이트) | **약 0.36 MB** |
| 래스터 (프레임당 타일 수십 장) | 프레임마다 요청 필요 |

0.36 MB는 현재 `index.html` 하나(6.7 MB)보다 훨씬 작다. **구간값은 전부 미리 받아 둘 수 있다.**

## 결정

**두 속도로 나눈다.**

| 사용자 동작 | 반응 |
|---|---|
| 슬라이더 드래그 중 | 구간 라인 색과 시계열 차트가 **즉시** 갱신 (메모리에 있음) |
| 손을 뗀 뒤 | 해당 날짜의 위성 래스터 요청 (로딩 표시) |
| 유휴 시 | 인접 프레임 1~2개 미리 받아 둠 |

**슬라이더 눈금은 달력 날짜가 아니라 실제 관측일**로 둔다(ADR-002). 눈금이 불규칙하게 찍히는
모습 자체가 "관측이 드물다"는 정보를 전달한다. 눈금 아래에 회랑 피복률을 막대로 깔아, 어느
날이 전 구간 관측인지 한눈에 보이게 한다.

**지도 인스턴스는 프레임워크 렌더 사이클 바깥에서 관리한다.** 지도 객체를 상태에 넣으면
리렌더마다 재생성되거나 레이어가 중복 추가되고, 증상이 "느려짐"으로 나타나 렌더링 성능
문제로 오인되기 쉽다.

**기존 `index.html`의 6.7 MB 단일 파일 구조를 해체한다.** 데이터는 요청으로, 코드는 모듈로
분리한다. 성능 이전에 코드를 읽을 수 있게 하기 위해서다.

## 검토했으나 버린 안

**모든 자료를 요청 기반으로.** 구현은 단순하고 자료가 커져도 대응되지만, 슬라이더 조작이
눈에 띄게 둔해진다. 구간값이 0.36 MB에 불과하므로 그럴 이유가 없다.

**래스터까지 전부 선로드.** 재생이 끊기지 않지만 첫 로딩이 무거워지고 모바일·저속 회선에서
불리하다.

## 결과

**좋아지는 것**
- 반응은 즉각적이면서 영상은 정확한 상태가 된다.
- 차트·구간색과 래스터의 갱신 시점이 분리되어 각각 최적화할 수 있다.

**나빠지는 것**
- 클라이언트가 두 종류의 시간 상태를 들고 있어야 한다(선택된 날짜 / 실제 표시된 래스터 날짜).
- 둘이 어긋난 순간을 UI가 알려야 한다. 그렇지 않으면 사용자가 다른 날짜의 영상을 보게 된다.

## 재검토 조건

- 구간 수가 늘어(4대강 확장 등) 선적재 크기가 수 MB를 넘을 때.
- 프레임 수가 크게 늘어 메모리 부담이 생길 때.
