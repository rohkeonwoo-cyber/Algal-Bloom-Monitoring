# ADR-004 · 지도 표출에 동적 타일 서버를 쓴다

- 상태: 채택
- 날짜: 2026-09-16

## 맥락

위성 산출물을 지도에 올리는 방법은 크게 두 가지다. 배치 때 PNG 타일을 미리 만들어 정적
호스팅하거나, 요청 시 COG에서 렌더해 주는 타일 서버를 두는 것이다.

저장 규모는 어느 쪽이든 문제가 되지 않는다(ADR-003: 연 0.33 GB). 판단 기준은
**등급 임계값·색상표를 사용자가 바꿀 수 있어야 하는가**와 **무엇을 증명하는가**였다.

기존 방식(`index.html` 6.7 MB 단일 파일에 데이터 내장)은 값 표현을 바꾸려면 산출물을 전부
다시 만들어야 했다.

## 결정

**COG를 원천으로 두고, 요청 시 렌더하는 타일 서버를 둔다.**

세 계층으로 역할을 나눈다.

| 계층 | 형태 | 역할 |
|---|---|---|
| 원천 | COG (수체 화소, 값 + 경과일 2밴드) | API 질의, 다운로드, 재처리 |
| 표출 | 동적 타일 | 지도 렌더링 |
| 요약 | 지점·구간 테이블 (PostGIS) | 시계열 차트, 검색·필터, 순위 |

**값과 경과일은 서버에서 한 장으로 합성해 내보낸다.** 별도 레이어로 겹치면 타일 요청이 2배가
되고 두 레이어의 로딩 시점이 어긋나 화면이 깜빡인다. 표현 강도는 타일 URL 파라미터로 조절한다.

**벡터타일은 쓰지 않는다.** 구간 폴리라인은 1,340개 · 91 KB(`flood/chla.json`)로, GeoJSON으로
충분하다. 4대강으로 넓혀도 500 KB 수준이다.

## 검토했으나 버린 안

**사전 생성 PNG 타일.** 서버 부하와 비용이 0이고 장애 요소가 없다는 큰 장점이 있다. 그러나
임계값을 바꿀 때마다 전체 재생성이 필요하고, 화면 범위 잘라 받기 같은 기능을 만들 수 없다.
**타일 서버를 띄울 수 없는 상황이 되면 이 안으로 되돌아간다**(ADR-005의 폴백과 연동).

**벡터타일 도입.** 현재 피처 수에서는 파이프라인만 복잡해진다. 피처가 수만 개를 넘을 때가
전환 시점이다.

## 결과

**좋아지는 것**
- 사용자가 등급 기준을 바꿔 볼 수 있고, 화면 범위 잘라 받기를 COG 부분 읽기로 자연스럽게
  구현할 수 있다.
- 산출물이 아니라 시스템이 남는다.

**나빠지는 것**
- 서버가 항상 떠 있어야 하고, 타일 캐시 전략이 필요하다.
- 서버 장애가 곧 지도 장애가 된다. 헬스체크와 폴백이 필요하다.

## 재검토 조건

- 배포처를 확보하지 못해 상시 실행 서버를 둘 수 없게 될 때.
- 트래픽이 늘어 동적 렌더가 병목이 될 때(그때는 캐시 계층을 먼저 넣는다).
